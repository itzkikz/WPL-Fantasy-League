# WPL Fantasy League

## Repo layout (what actually runs)

This is a two-package app. There is **no root package.json / workspace**; install and run commands separately in each package.

- `server/` — Node.js + Express + TypeScript API. CommonJS, compiled to `dist/` by `tsc`. Entry: `server/src/index.ts`. Uses Mongoose/MongoDB (`MONGO_URI`), Supabase storage, external football APIs, Puppeteer scraping. Data sources and models live under `server/src/{controllers,models,routes,services,scripts}`.
- `ui/` — React 19 + Vite SPA (TanStack Router + Query, Zustand, Tailwind v4, PWA). ESM. Runs in `ui/`.

## Setup / env

- `.env` files are gitignored (with `credentials.json`, `private.key`, `public.key`). `server/.env`, `ui/.env(.local)` and apps' `.env` are all required for dev; do not commit secrets or create fake values that work around them.
- Server expects `MONGO_URI`, `PORT`, `SECRET_KEY`, plus football-API / Supabase / Google / VAPID vars.

## Commands

Run inside the relevant package directory:

- `server`: `npm run dev` (nodemon, ts-node), `npm run build` (tsc -> `dist/`), `npm start` (node `dist/index.js`). Seed/recompute one-offs are `npm run seed:*` / `npm run recompute:stats` (ts-node under `src/scripts/`).
- `ui`: `npm run dev`, `npm run build`, `npm run lint` (ESLint). There is **no test script** in this repo — do not invent one.

## Gotchas

- `apps/` (`ui-admin`, `ui-fantasy`) and `packages/` (`server-*`) contain only empty `src/` dirs and stale build artifacts — ignore them; the live code is `server/` + `ui/`.
- TanStack Router codegen: `ui/src/routeTree.gen.ts` is auto-generated by the Vite plugin on dev/build — never hand-edit it; edit route files instead.
- PWA uses a custom service worker `ui/src/sw.ts` (injectManifest strategy per `vite.config.js`), not generateSW.
- Server uses `ts-node` for scripts while the app itself compiles with plain `tsc` — keep `src/scripts/*.ts` runnable under ts-node (CommonJS).
- `stdout`-logging middleware exists; per-route log/error patterns follow `server/src/middlewares/`.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

When the user types `/graphify`, use the installed graphify skill or instructions before doing anything else.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- Dirty graphify-out/ files are expected after hooks or incremental updates; dirty graph files are not a reason to skip graphify. Only skip graphify if the task is about stale or incorrect graph output, or the user explicitly says not to use it.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
